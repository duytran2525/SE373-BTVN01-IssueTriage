3. Hiện tượng Phân mảnh Byte (Token Fragmentation)

Khảo sát trên câu mẫu: "Cụm tìm kiếm gặp sự cố": 

1. cl100k_base (16 tokens):
   Token [00] ID=34     Raw bytes=b'C'
   Token [01] ID=51583  Raw bytes=b'\xe1\xbb\xa5'   <-- Dấu nặng 'ụ' bị bẻ thành mảnh byte lẻ
   Token [02] ID=76     Raw bytes=b'm'
   Token [03] ID=259    Raw bytes=b' t'
   Token [04] ID=24439  Raw bytes=b'\xc3\xac'       <-- Dấu huyền 'ì' bị bẻ thành mảnh byte lẻ
   ...

2. o200k_base (8 tokens):
   Token [00] ID=34     Raw bytes=b'C'
   Token [01] ID=2503   Raw bytes=b'\xe1\xbb\xa5'
   Token [02] ID=76     Raw bytes=b'm'
   Token [03] ID=71338  Raw bytes=b' t\xc3\xacm'    <-- ' tìm' được nhận diện thành nguyên âm tiết đơn token!
   Token [04] ID=125919 Raw bytes=b' ki\xe1\xba\xbfm'<-- ' kiếm' gom gọn thành 1 token duy nhất!

Nhận xét học thuật: Tiếng Việt sử dụng bảng mã UTF-8 gồm 2-3 bytes cho các ký tự có dấu thanh. Vì thuật ngữ huấn luyện BPE thiên về tiếng Anh, các âm tiết tiếng Việt thường bị bẻ nhỏ thành từng mảnh byte độc lập trong cl100k_base, đẩy số token lên gấp 1.5 - 4.5 lần so với tiếng Anh. Việc nâng cấp lên o200k_base với kho từ vựng mở rộng giúp dung nạp nhiều n-gram tiếng Việt hơn, giảm rõ rệt 40-50% số token tiêu hao, trực tiếp hạ thấp chi phí API và độ trễ phản hồi.

Phần 4: Chi tiết Demo 02 — Structured Output & Application Validation

1. So sánh Prompt-Only JSON và Structured Output

Yêu cầu mô hình trả về JSON bằng cách mô tả trong prompt (Prompt-Only) là hành vi mang tính xác suất (dựa vào năng lực instruction-following của LLM). Mô hình có thể vi phạm định dạng: bao bọc bởi markdown block ```json, thiếu trường bắt buộc, hoặc sinh các giá trị enum không tồn tại (như "Critical" thay vì "P0"). Ngược lại, Constrained Structured Output cưỡng chế quá trình giải mã (Constrained Decoding) theo JSON Schema.

2. Thẩm định Ngữ nghĩa độc lập tại Application (R4)

Điểm cốt lõi: Hợp lệ cú pháp Schema ≠ Hợp lệ quy tắc nghiệp vụ.
Provider/Gateway chỉ đảm bảo đầu ra khớp cấu trúc Schema, nhưng không thể kiểm soát các ràng buộc ngữ nghĩa chéo (Cross-field Invariants). Do đó, Application bắt buộc phải tự thẩm tra bằng model_validate_json ở tầng ứng dụng.

Quy tắc bất biến (Invariant) được hiện thực trong Pydantic validator:

@model_validator(mode="after")
def validate_application_invariants(self):
    if self.severity == "P0" and not self.needs_urgent_response:
        raise ValueError("Lỗi bất biến: Khi severity='P0', needs_urgent_response bắt buộc là True.")
    return self

3. Kết quả Thử nghiệm Negative Control Fixtures (Phần C - Offline)

Phần 5: Chi tiết Demo 03 — Function Calling & 4-Stage Trace (R5, R6)

1. Nguyên lý Vòng lặp Agentic (Agentic Tool Loop)

Mô hình ngôn ngữ lớn không bao giờ tự thực thi mã lệnh. Trong cơ chế Function Calling, model chỉ đóng vai trò phân tích yêu cầu và phát sinh một đề xuất có cấu trúc (Tool Proposal). Application giữ quyền kiểm soát toàn diện: nhận đề xuất, kiểm tra an ninh trong allowlist, thực thi hàm nội bộ an toàn và trả kết quả ngược lại cho model.

2. Bốn giai đoạn Trace tường minh (Numbered 4-Stage Trace)

=== 1. Model đề xuất tool call (Stage 1: tool_call) ===
{
  "call_id": "call_98xfa2...",
  "tool_name": "get_component_owner",
  "arguments": { "component": "payment" }
}

=== 2. Application thực thi (Stage 2: application executes) ===
   [Thẩm định allowlist: 'payment' in ['payment', 'identity', 'search']] -> Hợp lệ ✔
   get_component_owner('payment') -> 'checkout-platform'

=== 3. Tool result quay lại model (Stage 3: tool_result) ===
{
  "component": "payment",
  "owner": "checkout-platform",
  "status": "success"
}

=== 4. Final response từ model (Stage 4: final response) ===
Issue thanh toán bị lỗi HTTP 500 thuộc phân hệ Payment. 
Team chịu trách nhiệm xử lý là checkout-platform. Đây là sự cố nghiêm trọng cần ứng cứu khẩn cấp.

Phần 7: Các Quyết định Thiết kế Kiến trúc Cốt lõi

  1. Tách biệt Instruction và Input (R2): Không bao giờ nối chuỗi chung System Prompt với User Input. Toàn bộ nội dung issue được bọc trong delimiter <issue>...</issue> và áp dụng bộ lọc xóa thẻ đóng giả lập nhằm triệt tiêu nguy cơ tấn công prompt injection phá vỡ cấu trúc.
  2. Ranh giới Tin cậy (Trust Boundary - R5): Xem LLM là vùng không tin cậy (Untrusted Zone). Hàm execute_tool_call luôn kiểm tra đối số nghiêm ngặt thông qua allowlist và trả về dict chứa lỗi thay vì để ngoại lệ làm đổ vỡ vòng lặp agent.
  3. Defense-in-Depth phía Application (R4): Không ỷ lại vào gateway hay provider. Ngay cả khi có JSON Schema từ provider, Application vẫn luôn xác thực lại bằng Pydantic model và kiểm tra ràng buộc ngữ nghĩa liên trường.
  4. Thang bậc Dự phòng Linh hoạt (Fallback Hierarchy): Hỗ trợ luân chuyển mượt mà giữa client.beta.chat.completions.parse, json_schema và json_object, giúp hệ thống hoạt động ổn định trên mọi nhà cung cấp tương thích OpenAI (Gemini, OpenAI, Groq, Ollama).

Phần 8: Hạn chế Hệ thống & Đánh giá Rủi ro Dư thừa

  • Rủi ro Dư của Prompt Injection: Mặc dù kỹ thuật delimiter và system prompt giúp loại trừ các đòn tấn công phá vỡ thẻ đóng cơ bản, các kỹ thuật bẻ gãy ngữ cảnh tinh vi (semantic jailbreak) vẫn có thể khiến LLM hiểu nhầm ý định phân loại.
  • Xấp xỉ của Tokenizer: Kết quả đo đạc từ tiktoken chỉ phản ánh chính xác các mô hình của OpenAI. Đối với các nhà cung cấp khác như Gemini (dùng SentencePiece) hay Claude, tỷ lệ phân mảnh thực tế có thể có sự biến thiên nhất định.
  • Dữ liệu Giả lập (Mock Data): Danh bạ phân công COMPONENT_OWNERS hiện là dữ liệu in-memory mẫu. Trong môi trường doanh nghiệp thực tế, cấu phần này cần được kết nối tới cơ sở dữ liệu dịch vụ Service Registry (như Backstage hoặc CMDB).
